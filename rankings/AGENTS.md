## Second Quint Rankings app

Spec: `../.scratch/rankings/spec.md`. Tickets: `../.scratch/rankings/issues/`. Vocabulary: `../GLOSSARY.md`.

### Running

- `npm run db:start`: start local Supabase (Docker) and write `.env.local`
- `npm run dev`: app at http://127.0.0.1:3000
- `npm run db:reset`: re-apply all migrations from scratch
- New schema: `npx supabase migration new <name>`, then edit the file in `supabase/migrations/`
- Sample catalog: `supabase/seed.sql` and `public/samples/` are generated by `node scripts/generate-sample-data.mjs`; edit the script, not the outputs

### Layout

- `src/domain/`: pure rules and calculations, no I/O (bracket building, ranking calculation, allowance math)
- `src/server/`: the game, catalog, and admin services; take a `SupabaseClient` as their first argument
- `src/app/`: pages, route handlers, and server actions; thin wrappers over `src/server/`
- `src/lib/supabase/`: `createVisitorClient()` (acts as the visitor, respects row-level security) and `createAdminClient()` (server-only, full access)

- `src/lib/session.ts`: who is playing. `readPerson()` / `ensurePerson()` give the signed-in player or the signed-out visitor; game service functions take either (`Person`). `src/proxy.ts` refreshes the Supabase session cookies.

`cacheComponents` is off: pages render dynamically.

### Environment variables

`npm run db:start` writes all of these to `.env.local` for local work; production values go in Vercel.

- `NEXT_PUBLIC_SUPABASE_URL`, `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY`: the Supabase project, safe for the browser
- `SUPABASE_SECRET_KEY`: full-access key for `createAdminClient()`, server-only
- `SUPABASE_DB_URL`: direct Postgres connection, used by scripts only
- `RANKINGS_REFRESH_SECRET`: shared secret for `POST /api/rankings/refresh` (bearer token). Supabase pg_cron calls it every 5 minutes using the URL and secret stored in Vault (`rankings_refresh_url`, `rankings_refresh_secret`); without both Vault secrets the job does nothing, as locally. Setup: `docs/ops.md`

### Global rankings

The ranking refresher (`refreshGlobalRankings` in `src/server/rankings.ts`) recomputes every global ranking with the pure calculation in `src/domain/ranking/` and stores one ready-made list per scope and version (`ranking_lists.rated`: rated lists use only rated matches, unrated lists every match; `ranking_entries`); ranking pages only read those rows, showing the rated version unless the URL has `?version=unrated`. The default category cover is the top of the category's rated list. Service tests call `refreshGlobalRankings` directly instead of waiting for the schedule.

### Contestant page

`/contestants/[id]` (`?version=unrated`) reads `getContestantStanding` (`src/server/rankings.ts`): the contestant's entry in the latest stored Overall and Category Rankings of that version (null = not yet judged), its live record and most frequent opponents from the `contestant_head_to_head` SQL function, and each scope's weekly rating history. The first refresh of each New York week (Monday to Sunday, `snapshotWeek` in `src/domain/ranking/`) stores one `rating_snapshots` row per scope with judged contestants, from the rated lists only, with an entry per judged contestant (`store_rating_snapshot` skips a scope that already has the week's snapshot). Snapshots are never pruned; the chart (`rating-chart.tsx`) is an inline SVG.

### Personal rankings and profiles

`getPersonalRanking` (`src/server/rankings.ts`) computes a player's personal ranking on every request from only their own non-excluded matches, with no fading (`halfLifeDays: null`); nothing is stored and the refresher isn't involved. `listPersonalRankingScopes` lists Overall plus the categories they've played. The profile (`/players/[name]`, `?scope=<category ID>`, `?version=unrated`) shows these and `listPastTournaments` (`src/server/game.ts`, latest 50) to anyone through the visitor client.

### Rated allowance

The allowance size and the New York day boundaries are pure (`src/domain/allowance/`); `tournamentRatedStatus` decides rated or unrated with the reason, and the start page uses it to tell the player before starting. The game service enforces it in the `start_tournament` SQL function, which locks the player's row so the one-unfinished-rated-tournament check and the reservation in `allowance_use` (per player, scope, and day; only ever added to) can't race. Service functions take an optional `now` so tests can cross midnight. Hand-picked tournaments (`startTournament` with `contestantIds`; the start page's "Pick contestants", which loads the scope's contestants from `listScopeContestants` via `?pick=<scope>`) are stored with `hand_picked` and are always unrated: `start_tournament` never rates them or touches `allowance_use`, and "hand-picked" is the reason shown ahead of any other. Tournament picks never touch `allowance_use`, so a rated tournament resumed on a later day stays rated for free. `giveUpTournament` sets status `given_up` (only from an unfinished rated tournament) and refunds nothing; `pickWinner` and `undoLastPick` only update unfinished tournaments, so they can't revive one. `UnfinishedTournaments` (`src/app/unfinished-tournaments.tsx`) is the resume banner on the home page, the player's own profile, and the start page.

### Infinite Mode

`getInfinitePair` offers each person one pair per scope, stored in `infinite_pairs` so a reload shows the same pair; `pickInfiniteWinner` and `skipInfinitePair` delete that row first (so a pair is picked or skipped once), and the next `getInfinitePair` draws a new pair with the pure `pickInfinitePair` (`src/domain/infinite/pairing.ts`) using the scope's latest stored rated ranking list. A signed-in player's pick is rated while they have allowance left in the scope: the `pick_infinite_pair` SQL function claims the pair, adds 1 to `allowance_use`, and records the match in one transaction, locking the player's row like `start_tournament`. While a pick would be rated, skips are limited to `RATED_SKIPS_PER_DAY` (5) per player per New York day across all scopes (`skip_use`, enforced by `skip_infinite_pair`); unrated skips are unlimited. Choosing unrated (`?play=unrated`, the `unrated` option) gives a separate offered pair (`infinite_pairs.chose_unrated`), so free unrated skips can't clear the rated pair. `getInfinitePair` returns `play`: rated with picks and skips left, or the unrated reason. Infinite Mode never checks for an unfinished rated tournament. Pages: `/infinite` (scope list) and `/infinite/[scope]` (`all` or a category ID).

### Catalog and pictures

The catalog service (`src/server/catalog.ts`) adds and edits contestants and categories and enforces who may edit what (rules in `src/domain/catalog/permissions.ts`). Pictures are resized in the browser by `src/lib/picture/resize.ts` to center-cropped squares at 512 and 128 px (WebP; JPEG where the browser can't encode WebP), using the pure rules in `src/domain/picture/picture.ts`, which a server-side import with `sharp` can reuse. The server stores them in the public `pictures` Storage bucket (created by a migration) under the SHA-256 of their bytes, cached for a year. `contestants.source_id` is an internal, unique ID for bulk-imported contestants (e.g. `mal:12345`), never shown.

### Reports and moderation

Anyone (signed in or not) can report a contestant, category, or profile with a short reason (`reportItem` in `src/server/catalog.ts`, the `ReportForm` on those pages); a second report of the same thing by the same person while the first is open adds nothing. The admin service (`src/server/admin.ts`) is admin-only (`players.is_admin`, not banned): `listOpenReports` / `closeReport` (resolved or dismissed) back `/admin` (404 for everyone else, linked from the header), and `removeContestantFromCategory` / `deleteCategory` back the admin controls on the category page. The admin edits or deletes any contestant or category through the catalog service's normal functions. In the database, only the admin can read `reports` (row-level security via `private.is_admin()`), and `remove_from_category`, `delete_category`, and `delete_contestant` are service-role only.

- **Deleting a contestant** (creator before its first rated match, or the admin) deletes only its own matches. Tournaments that drew it get status `removed`: they can't continue or be undone, have no tournament ranking, and their other matches still count. Open reports about it are resolved.
- **Removing a contestant from a category** drops it from that category's stored rankings at once (the rest move up) and clears it as cover; its matches stay and still count toward overall, and refreshes leave them out of the category ranking because the calculation ignores non-members.
- **Merging duplicate contestants** (`mergeContestants`; on `/admin` the admin pastes two contestant links or IDs, reviews them with `previewMerge`, and confirms) runs the service-role-only `merge_contestants` SQL function in one transaction: the duplicate's matches, memberships, covers, and offered Infinite Mode pairs move to the survivor; matches (and offered pairs) between the two are dropped; the survivor takes the duplicate's bracket slots, and tournaments that drew both become `removed`; the duplicate leaves the stored rankings at once and the survivor's entries catch up at the next refresh; open reports about the duplicate are resolved. The duplicate's row stays with `merged_into` set (earlier merges into it are re-pointed), so `/contestants/[id]` permanently redirects via `findMergeSurvivor`, and its weekly rating snapshots stay on it. Its `source_id` moves to the survivor unless the survivor has its own; an importer that finds a merged contestant by `source_id` must follow `merged_into`.
- **Renaming and banning players** (`renamePlayer`, `banPlayer`, `unbanPlayer`, `getBanStatus`; the admin controls on `/players/[name]`, not on the admin's own profile). Renaming uses the same display-name rules as choosing one and moves the profile to the new name. A banned player is refused by every game service function that plays (`startTournament`, `pickWinner`, `undoLastPick`, `getInfinitePair`, `pickInfiniteWinner`, `skipInfinitePair`; `isBanned`), by the catalog service, by `reportItem`, and by the admin service. The service-role-only `set_player_ban` SQL function sets the flag and, in the same transaction, sets `matches.excluded` on all the player's matches: banning with "remove matches" excludes them, banning without it or unbanning un-excludes them. Every ranking read (`refreshGlobalRankings`, `getPersonalRanking`, `contestant_head_to_head`) skips excluded matches, so global rankings change at the next refresh; tournament rankings still replay all of a bracket's matches. The admin can't ban themselves.
- **Deleting a category** deletes its memberships, rankings, and snapshots; its matches and tournaments keep going with no category (so they count toward overall only), and its unfinished tournaments become `removed`.

### Test seams

- **Unit** (`npm test`): `src/**/*.test.ts`, pure domain code, including the ranking calculation
- **Service** (`npm run test:service`): `tests/service/**/*.test.ts`, calls `src/server/` against the local Supabase; files run one at a time
- **Browser** (`npm run test:e2e`): `e2e/*.spec.ts`, Playwright at a phone viewport against a production build; keep these few and about wiring, not rules. `e2e/auth-stub.ts` signs a browser in without Google (admin-issued magic link), so the app has no test-only sign-in route
